# YuE2 music pipeline (GB10): generate, cover, get editable scores

YuE2 (HKUST / M·A·P) turns lyrics + style into a full song WITH an editable symbolic score, and (via SheetSage2) transcribes a recording into that score for zero-shot covers. The user's recurring goal: **mp3 in → rock/metal arrangement → guitar score**. On GB10 the models run on the 128 GB unified GPU; Windows/ComfyUI is a separate optional GUI (not part of this pipeline).

## Layout (verify live first)
```
~/YuE/                       git clone; two venvs:
  .venv                      YuE2 — Python 3.12 + torch cu128 (generation)
  .venv-sheetsage2           SheetSage2 — Python 3.11 (transcription; NVRTC sm_121 bug)
  models/SheetSage2/         SheetSage2 weights (gated HF repo)
  outputs/<job>/             per-job artifacts (served at :8090)
~/yue2/                      yue2-backend.py (:1540), yue2-proxy.py (:11540)
~/ComfyUI/                   ComfyUI venv (py3.12, torch 2.14.1+cu130) :8188
  custom_nodes/YuE2-ComfyUI/ pytraveler pack — Transcribe + GenerateSong + LoRA nodes
  models/loras/              ar_lora_inst_v3abc.safetensors (instrumental, 267M)
  output/audio/              ComfyUI-generated songs
~/.config/systemd/user/      yue2-backend.service, yue2-proxy-40.service,
                             comfyui.service, yue2-outputs-http.service (:8090)
~/.cache/huggingface/hub/    symlink → /home/joons/models/ (YuE2-3B, YuE2-Vae)
```
Ports follow the GB10 115XX-front / 15XX-back convention: **11540** front (LAN 0.0.0.0) / **1540** back (127.0.0.1).

## The pipeline (in order)
1. **Transcribe** the source mp3 with SheetSage2 → `score.abc` (melody). Use `.venv-sheetsage2`.
2. **Cover/arrange** with YuE2 `cot="melody"` + `abc=<that file>` + target style/lyrics → new `audio.flac` + `score.abc`. Use `.venv`.
3. **Guitar score** from the cover: demucs guitar stem → basic-pitch → GP5 (the `guitar-tab-transcription` path), NOT the full mix.
4. **Multi-part scores** (e.g. guitar/bass/drums): parse the cover's `score.abc` — guitar = the Ins-staff riff as-is, bass = chord roots as quarters, drums = authored pattern (kick 8ths + snare on beats 2/4, hi-hat as separate staff). YuE2 emits ONE melody, never 3 parts.
   - **The user's guitar deliverable is ONE .gp5 with two tracks**: `guitar riff` (the 4-bar Ins riff looped over the whole song, 8th-note resolution) + `power chords` (root+5th on strings 5/6, one chord per bar), with chord-name annotations (`C5/F5/G5`) on the first beat of each bar. Riff extraction: the Ins staff packs 4 bars per line separated by `|` — collect the `V: Ins` lines, split, and take the verse 4 bars; re-emitting the raw line as a single ABC line gives one 16-note "measure".
   - **Every ABC part: one measure per line, 4 beats in 4/4**, program-verified by summing note values per line (strip `"C"` chord-name prefixes first). Multi-measure lines or overfull measures are what the user reports as broken 10/16-beat bars.
   - **Write the style prompt to specify structure**: sections (intro / verse / chorus / bridge / outro with the main riff bookending) and an explicit varied chord progression (e.g. "Dm Gm Bb C with movement in every section, never a single static chord"). Left to its default, YuE2 collapses to a 2-bar riff loop with one static power chord — the user reports this as too simple.
   - **Structured audio ≠ structured score.** Even with a section-specified prompt, the model's `score.abc` usually stays a 2-bar riff loop (only `% section` markers appear, the note content does not vary). The audio IS structured; the symbols are not. Build the part set by transcribing the loop cell(s) literally and placing them into the section layout YOU design (intro/verse/chorus/bridge/outro bar counts summing to the audio length, e.g. 180 s @120 BPM = 90 bars), with the chord progression advancing across sections — do not parse section content out of the model's ABC.
   - **Practice (backing) track**: never by generating the song twice — a second generation is a different song, so the guitar track won't align. The same-song backing track is the audio with the guitar stem removed (demucs). On GB10 aarch64 `pip install demucs` can fail building its `sphn` dep — fallback: synthesize bass+drums directly with numpy+soundfile (`~/YuE/.venv` has both): quarter-note bass (saw partials, exponential decay env), pitch-drop sine kick on 1&3, noise+190 Hz snare on 2&4, diff-noise hi-hat on 8ths, normalize to −1 dB, 16-bit WAV. Disclose that it is a synthesized groove, not the original drum take. The practice bass must follow the SAME progression as the score (per-bar roots, 8th-note drive in the chorus) — a single static bass note reads as "too simple" for the same reason the user rejected one static power chord; chorus drums = 16th grid with double kick.
   - **GP5 build**: PyGuitarPro — `Beat.start` is an offset from the measure start (quarters at 0/240/480/720 in 4/4; a full-measure multiplier collapses beats onto bar 1), and chord annotations go on `beat.effect.chord` (gp4 writeBeat serializes it for GP5 too). Full API pitfalls: `guitar-tab-transcription` skill → `references/gp5-writing.md`. Verify with `guitarpro.parse` AND by printing per-measure `beat.start` values — note counts alone miss collapsed beats.

**Instrumental (no-vocal) songs** need the ComfyUI path with the LoRA — see "ComfyUI queueing" below. The plain backend ignores "no vocals" in the style text.

Run transcription and generation **sequentially** — they share one GPU, and running both at once thrashes unified-memory bandwidth.

## ComfyUI queueing (instrumental + GUI-independent)
ComfyUI at :8188 runs the same YuE2 models plus the `pytraveler/YuE2-ComfyUI` pack (16 nodes). Queue without a browser via POST `/prompt` (NOT `/queue/prompt` — 405):
1. **Node class names drift between pack updates** — after a ComfyUI restart or pack upgrade, previously-hardcoded `class_type`s may be missing entirely. Before building the payload, enumerate the live registered types (filter `object_info` keys by `yue`/`music` — the full dump times out, use per-node queries or a quick filtered fetch) and cross-check against the example workflow JSON; the current pack's generation path is the modular `YuE2GenerateSong` + `YuE2Options`/`YuE2LoRA` graph, not a single generate-music node. Load example workflow JSON (`12 - An instrumental.json`), build the API payload: skip non-registered node types (MarkdownNote), map `widgets_values` to `object_info` spec names **per-node** (UI widget order ≠ spec order — generic positional mapping fails validation with KeyError). The POST body is `{"prompt": {node_id: {"class_type": <type>, "inputs": {...}}}, "client_id": <str>}` — a bare nodes dict fails with `no_prompt`, and a node missing `class_type` fails with `missing_node_type`. Current pack's exact wiring (verified live): `YuE2GenerateSong` inputs = `style` (text), `lyrics` ("[instrumental]"), `seed` (int — the seed lives HERE, not in options), plus optional link inputs `options` = `["<options_node>", 0]` and `lora` = `["<lora_node>", 0]`; `YuE2Options` spec names = `cot`, `max_seconds`, `keep_model_loaded`, `abc_temperature`, `repetition_penalty` (there is NO `seconds`/`seed` spec — unknown input names fail validation); `SaveAudioAdvanced` = `audio` link + `filename_prefix` + `format`. Generation takes ~7–10 min end-to-end. `YuE2LoRA.loras` is a **JSON string** (`json.dumps([{"name": ..., "ar": 1, "nar": 1, "on": true}])`), not a Python list — a list fails with `bad_linked_input`.
2. Instrumental: `YuE2LoRA` node (full `/object_info` is too slow — query specs per node, see Pitfalls) with `ar_lora_inst_v3abc.safetensors`, keep `cot="full"` (changing to `melody` brings vocals back), lyrics = `[instrumental]`.
3. Poll `GET /queue` (running/pending both empty = done; queue entries are `[pos, prompt_id, ...]` so a per-prompt match must use `p[1]` — an off-by-one index reports "done" while the job is still running and `/history` is empty, so an empty history after a "done" poll means false match, keep polling) then `GET /history/<prompt_id>`; the score ABC comes back in the response (`outputs.<id>.yue2_score`) — it is NOT saved to disk; copy it to `~/YuE/outputs/` for the :8090 link. The audio does NOT always land in `output/audio/` — it has appeared at the `output/` root too; locate it with `find ~/ComfyUI -name <output_prefix>*` before copying.
4. LoRA prefers ~2–3 min output; short-length requests in the style text get ignored.

The user couldn't reach the ComfyUI browser UI from Windows — prefer queueing from GB10 via API.

## User request template (standard order for practice songs)
The user's recurring order: an instrumental practice song + complete sheet-music set. They paste a 5-line template:
```
연주곡 하나 만들어줘
- 장르: (heavy metal / hard rock / R&B)
- BPM: (default ~140)
- 길이: within 3 minutes
- 난이도: beginner guitar (riff + power chord) | intermediate (riff + power chords, non-repetitive)
- 보컬 없음 (instrumental)
```
**Intermediate delivery set:** guitar splits into TWO parts, so ship 5 ABC + 5 MIDI + audio: `guitar_riff`, `guitar_powerchords`, `bass`, `drums`, `practice_bass_drums`. "4분 전후" / "4분 이내" length requests are the same class — 4분 전후 may land 3:00–4:00. **Never edit a submit script with a broad search-and-replace (e.g. replacing the bare digit 4)** — it corrupts every "4" in the payload including ComfyUI node ids and breaks the save node; replace only full unique strings (seed number, prefix, max_seconds value), or rewrite the file with write_file.
Fixed delivery spec (do all of it without being asked):
1. ComfyUI API + instrumental LoRA (no vocals), ~2–3 min output
2. Four parts: `guitar` (2-track GP5 + ABC), `riff` (ABC), `bass`, `drums` — all ABC one measure per line, chord names on each bar's first beat
3. Guitar GP5 = `guitar riff` track (verse 4-bar loop, 16th-note resolution) + `power chords` track (root+5th strings 5/6, one chord per bar) + chord annotation (`C5`-style, with diagram firstFret/strings) on each bar's first beat
4. Verify before shipping: `guitarpro.parse` each GP5 → every measure's total beat `duration.time` == 3840 (4/4); every ABC line (strip `"X"` chord prefixes) sums to exactly 4 beats (a bare note with no value = 1 unit at the L: resolution — counting it as 0 gives false "underfull" failures); every MIDI loads back with `mido` and its total playback duration == expected seconds
5. Copy everything to the delivery folder `/home/joons/Music/<YYYY-MM-DD>[_NN]/` and post the audio FLAC via MEDIA: (the :8090 outputs copy + links apply when the user works from the Windows box). Anything missing from the user's message (no-vocals / riff / chord names / GP5) is exactly what has been omitted before — never ship without all of it. **The fixed spec fills gaps, it never overrides an explicit list:** when the user names their deliverables (e.g. "abc 4 + midi 4" with no GP5), ship exactly that set — adding un-requested artifacts (GP5) gets them stripped out later.
**Audio-first mode:** when the user asks to deliver the song first and decide on the scores afterward ("곡 먼저 생성해서 공유"), ship ONLY the audio FLAC (MEDIA + :8090) and stop — wait for approval before building ABC/MIDI/GP5.

## Standing rules
- **Two separate venvs, never shared.** YuE2 wants torch 2.10 / py3.12; SheetSage2 wants torch 2.8 / py3.10–3.11. Mixing them breaks one of the two.
- **Deliver the audio** — the user wants to HEAR each generated/covered song. Send `outputs/<job>/audio.flac` via MEDIA:.
- **The score is ABC, not MIDI.** YuE2 has no direct MIDI output. ABC (2-part melody by default; chords only with `cot="full"`) is the editable score and the better input for → sheet music.

## Pitfalls (rule first; why in a clause)
- **aarch64 `pip install .` pulls the torch CPU wheel by default.** Force the CUDA build from `download.pytorch.org/whl/cu128`, then reinstall torch WITHOUT `--no-deps` so pip resolves the matching `nvidia-*` libs — chasing them by hand is version whack-a-mole. (details: references/install-serving.md)
- **GB10 is sm_121; torch 2.10's max supported arch is sm_120 → a warning fires but it WORKS via JIT.** Verify with a real matmul + bf16 before trusting it; don't "fix" a working setup just because of the warning.
- **Lazy-load the pipeline OUTSIDE the lock.** The on-demand backend's loader acquires the state lock; calling it inside the handler's own `with _lock:` block deadlocks the backend on the FIRST request — the proxy tunnels the POST but the backend logs nothing and `/health` hangs. (details: references/install-serving.md)
- **`truncated: true` = the song hit its context limit and stopped short** (e.g. 68 s of a longer piece). Retry with a different seed or shorter lyrics; don't ship the cut version as complete.
- **`uv venv` does not install pip.** `python -m pip` and `huggingface-cli` come up missing; use `uv venv --seed` or `uv pip install --python <venv>/bin/python pip <pkgs>`.
- **SheetSage2 is a GATED HF repo** — `huggingface-cli login` + granted repo access are required before the model download; budget for that approval.
- **SheetSage2 NVRTC bug on sm_121:** torch 2.10+cu128's NVRTC 12.8 rejects sm_121 (`nvrtc: error: invalid value for --gpu-architecture`) the moment any SDPA/cast kernel JITs; `TORCH_CUDA_ARCH_LIST` and fp32 don't help. Workarounds: ComfyUI's Transcribe node (torch cu130, NVRTC OK) or upgrade the venv to torch ≥2.11/cu129+.
- **transformers remote-code cache for SheetSage2** drops local `.py` files (`chord_spelling_sheetsage2.py` FileNotFoundError) — copy the model dir's `.py` files into `~/.cache/huggingface/modules/transformers_modules/SheetSage2/`.
- **ComfyUI venv torch:** let requirements overwrite to 2.14.1+cu130 (first-party sm_121 support); don't downgrade to match the YuE venv — they are separate venvs by design.
- **Model ABC note names are key-signature-relative.** Resolve accidentals (`^G`, `^^G`) against the `K:` sig when converting to MIDI numbers — a transcription slip shows up as MIDI pitch error while ABC line-length checks still pass, so verify pitch values, not just duration sums. The same is true for HAND-AUTHORED builders: a copy-pasted chord dict that maps two different chords to the same pitch pair passes every unit/last_off assert — spot-check a few bars' actual pitches against the intended progression before shipping.
- **Chord labels ride on the Vocal staff in instrumental takes.** The per-bar `"D#m"`-style labels sit on the `V: Vocal` rest lines; the Ins staff carries none. Parse the Vocal line (one label per bar) for the power-chord/bass progression — don't assume the Ins staff has them or invent a cycle when the score already encodes one.
- **PyGuitarPro `Duration` value = note denominator, not a beat count.** `Duration(4)`=quarter, `Duration(8)`=eighth, `Duration(16)`=16th, `Duration(2)`=WHOLE-note-half (a half note = 2 bars of 4/4!). Mapping ABC 16th-units to durations is `{1: Duration(16), 2: Duration(8), 3: Duration(8, isDotted=True), 4: Duration(4)}`; a wrong map (e.g. 8th→`Duration(2)`) inflates one bar to 2.5–4× length and the user sees "10/16 beats per bar" in Guitar Pro even though note counts look right. Ticks: quarter=960, 4/4 bar=3840, 16th=240.
- **`writeBeat` never serializes `beat.start`** — beat position in the file is implied by order + duration, so re-parsing shows whatever start you set (it round-trips as a computed value). Don't debug layout through `start`; verify per-measure duration sums (3840 for 4/4) instead. `Beat.start` is still needed at build time for `getBeat()` lookups.
- **One token source for all three artifacts.** Author each bar once as token tuples (start-tick, units, pitch/hit) and generate the ABC, the MIDI, and the practice WAV all from that single structure. Divergence between them (MIDI 4 hits vs ABC 2 hits per bar) is the #1 rework cause — it can only happen if the artifacts are built independently. **To repeat a (pitch, units) tuple N times in a riff bank write `[(p,d)]*N` — never `[(p,d)*N]`:** the latter multiplies the tuple itself into ONE 2N-element tuple, which the per-bar `for p,d in row` unpack rejects at runtime ("too many values to unpack") or silently corrupts the grid if the row happens to unpack differently. This bug recurs across score-builder sessions — after any edit to a riff bank, grep the file for `)*[0-9]` inside note lists before first run.
- **Multi-voice ABC: staves are declared ONLY in the header** — one `V:name clef=X name="..."` line per voice; every body line carries ALL voices for that bar, joined by `/` in header order. A `V:` label mid-body is invalid and desynchronizes the voices.
- **Validate ABC at token level, pre-serialization** — assert 16th-units == 16 per voice per bar in the builder. Re-parsing the written text is a trap: the octave comma in `A,` is part of the note NAME, not a separator, so naive comma/char splits inflate unit counts (details: references/abc-midi-writing.md).
- **ANY inline multi-line Python hits the approval timeout** — `python3 -c "<multiline>"`, `python - <<'EOF'` heredocs, and execute_code all sit in approval waiting and stall the session; write the code to a `/tmp/*.py` file with write_file and run the file instead. File runs pass instantly, inline attempts stall.
- **`/object_info` (full) times out (~5 min) on the YuE2 pack** — query per node: `curl --max-time 20 http://127.0.0.1:8188/object_info/<NodeName>`.
- **mido chord (concurrent notes) tracks break the "per-track `sum(m.time)` == total" check** — N notes of one bar sum to N×bar, not 1 bar. Encode chords as a flat sorted event list `(abs_tick, on/off, pitch)` with note_on sorted before note_off at the same tick, then verify the LAST note_off's absolute time == total ticks (and assert `pos == TOTAL_TICKS` inside the builder). mido API: `mf.tracks = [t0, t1]` (MidiFile has no `.append`); `end_of_track` is a `MetaMessage`, not a `Message`. Verify length by walking the track's messages and accumulating `m.time` up to `end_of_track` — the `MidiFile.length` attribute has been observed reading a value inconsistent with the final tick (180 vs 172800), which can trigger a false "file broken" report on a correct file.
- **Design guitar tokens in playable register** — every pitch 40 (E2, low E string) .. 88 (E6); a D#5 power chord's 6th-string root (D#2=39) is BELOW the low E string and unplayable. Use the 5th-string-root shape (frets 2–8) for D#/C#/B chords; riff notes on one string (e.g. G-string, frets 2–11) read beginner-friendly.
- **ABC sharps are `^`, never `#`** — `D#` in a note token is parsed as note D + accidental # and breaks the 16-unit-per-line check (also looks wrong in renderers). The chord LABEL (`D#m` at line start) may use `#`; note names must not. Unit counting: parse per note+duration PAIR (`(?:[\^?v=x]*[A-Ga-gz'x][,\']*)(\d*)`) and sum group(1) (default 1) — a bare `\d+` scan merges consecutive durations (`22222222` → 22222222). Percussion staves: count chars (16 chars = 4/4 bar), the note regex misfires on `x` (snare looks like a sharp prefix).
- **mido `Message('program_change', channel=...)`: channel is 0–15, program is the GM number (24 = clean guitar, 33 = acoustic bass)** — passing the GM number as the channel raises `channel must be in range 0..15`. Drum channel = 9, no program_change. **`program_change` is a regular `Message`, NOT a `MetaMessage`** — `MetaMessage('program_change', ...)` raises `KeyError: 'program_change'` (it isn't in `_META_SPEC_BY_TYPE`); only `track_name` / `set_tempo` / `end_of_track` are meta.
- **Author riffs as MIDI pitches, derive ABC names from pitch** — keep ONE list of integer pitches per bar and compute the ABC token via a `pitch→note-name` function (`pc=p%12`, octaves from the C4=60 reference). Hand-writing ABC note names AND a parallel MIDI list is the #1 source of drift (a typo'd `EE` tie, a wrong octave comma) that passes duration checks but plays the wrong notes. Single-source = the two can never disagree.
- **Anti-repetition for metal/riff genres: `repetition_penalty≈1.7`, `abc_temperature≈0.9`, "distinct riff per section" in the style text.** The defaults (1.2 / 0.7) collapse to one 16th-note riff looped for the whole song on a single static chord — the user rejects this as "너무 반복." With the stronger penalty the model emits real per-section motifs + a 4-chord progression; regenerate (new seed) if a take is still a loop. **The judge is reading the extracted score.abc, not the audio:** a REJECT = the same Ins-staff 4-bar cell repeated across sections, or one/two chord labels (e.g. only `"D#m"`) on every line; an ACCEPT = distinct per-section motifs with a moving 4-chord progression. Budget ≥2 generations — with penalty 1.7 roughly half of first takes are still loops, so a rejected first attempt is normal, not a broken pipeline. For strict no-repetition requests ("리듬 반복 없음") budget ≥3 rolls even at 180 s — hard single-cell loops still occur (2 of 3 rolls in one session), and even an accepted take may be a 4–6-cell rotation with back-half cell reuse: disclose the actual repetition level instead of claiming zero repetition. **Length interacts with repetition:** takes at ~210–240 s collapse to a repeated cell in the back half of the song even at `rep_penalty=1.8` / `temp=1.0` (3 consecutive rejects at "4분 전후"; a 180 s take passed) — if the user insists on ~4 min, budget ≥3 regenerations and check the score's LAST third specifically for cell repetition, not just the opening sections. **Style-text tempo words override the "NNN BPM" number** — "slow-heavy ballad" produced Q:1/4=76 against a "120 BPM" request, and even with the adjective fixed the model can collapse to a different METER (2/4@60); "metal ballad" in particular fails the tempo request repeatedly. Verified workaround for ballad-style requests: drop the ballad wording and use "epic heavy metal, <N> BPM, emotional arrangement, tempo exactly <N> BPM" — where "metal ballad" collapsed to 2/4@60 across multiple seeds, this phrasing produced a native 4/4@120 take (still verify the `Q:` line, and the back-half repetition collapse still applies at ~210 s+). Keep tempo-adjectives consistent with the requested BPM and always verify the score's `Q:` line before building (a Q≠requested BPM means the score's bar math is wrong even if the audio sounds fine). When a take fails the requested tempo/meter, offer the user a numbered choice that includes "ship as-is": if the bar length matches (2/4@60 ≡ 4/4@120, same 2 s/bar), the score can be re-authored at the requested tempo over the same bar count and the audio delivered unchanged, with the mismatch disclosed.
- **`ticks_per_beat` must be a round multiple that gives a 4-beat 4/4 bar** — SPB=480 → bar=1920, 8th=240, 16th=120. SPB=96 gives 1920/96=20 "beats" and breaks every eighth/16th math (MIDI lands on the wrong grid).
- **mido lives in neither YuE venv** — `pip install mido` into `~/ComfyUI/.venv` (pure python, fast) and run the score builder with `~/ComfyUI/.venv/bin/python`; `python3`/`~/YuE/.venv` both lack it.
- **Power chords in ABC are dyad CHORDS `[root2 fifth2]`**, repeated per strum — never sequential notes (that plays a melody, not a chord). Unit counting for such lines: treat each `[...]` as ONE rhythmic slot whose duration = the first note's duration; a plain per-note regex double-counts it. MIDI side: one note_on/off pair per strum per pitch.
- **Generated audio length varies (180–240s)** even with max_seconds set — always `ffprobe` the FLAC and size the score (BARS = seconds/2 at 120 BPM) to the actual duration before building. **Match the audio to the ACCEPTED prompt_id, not to mtime or find-order:** retries with the same `output_prefix` leave several `*.flac` files in `output/audio/YuE/` (e.g. `_00001` from the rejected take, `_00002` from the accepted one); `GET /history/<prompt_id>` → the SaveAudio node's `outputs` gives the exact `filename`. Copying the newest file by timestamp picks the wrong take when the queue was re-run. The prefix date is arbitrary (a song generated the next day can still carry the previous day's prefix) — only the delivery folder date (today) must be correct. **The transcribed `score.abc` can also end BEFORE the audio and end mid-token** (a 210 s audio transcribed to a 180 s score whose final cell was a cut-off `F4F`): when the back half is a repeated cell, the truncation is safe to ignore, but always drop the trailing bar whose unit sum ≠ the L:-resolution total (32 at `L:1/32`, 16 at `L:1/16` — the transcribed score's resolution varies, so compute the expected total from the score's own `L:` line, not a hardcoded 16) before parsing, and size the build to the complete bar count. The raw transcribed score can ALSO be structurally unparseable — dotted-note overflow splits measures into extra lines, so raw `|`-line counts exceed the true bar count (a 180 s take transcribed to 109 lines of real 94 bars). Do not parse the raw lines 1:1; re-author the verified motifs onto a clean grid (bars = actual seconds ÷ 2 at 120 BPM) instead. **The score can ALSO end AFTER the audio** (a 113-bar score for a 90-bar / 180 s audio) — in that case take the FIRST BARS bars in order and drop the tail (never re-grid from the tail or pad the audio). A source score may also arrive at `L:1/32` instead of `L:1/16` — convert by halving every duration (1/32-based takes have even durations) and take the expected per-bar total from the score's own `L:` line.
- **Output dir per the user's spec:** `/home/joons/Music/<YYYY-MM-DD>/`; if it already holds a previous song the same day, append `_01`, `_02`… to the folder name.
- **mido data bytes are 0–127** — clamp both velocity and the note-on delta byte before writing (a final crash/long note held to the bar end overflows the byte and corrupts the file); verify length PER TRACK (`sum(m.time)` over one track — summing across tracks double-counts a multi-track file), and pad short tracks with a trailing `end_of_track` meta.
- **YuE2 backend has no LoRA support** — instrumental songs only via the ComfyUI path.
- **Deliver download links, not just MEDIA:** the user works from Windows; `:8090` (outputs) and `:8188/view` (ComfyUI output) are the LAN download points.
